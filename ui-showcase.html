B+ 树的非叶子节点不存数据，只存键和指针，同样大小的页能装下更多键，树更矮 → 磁盘 IO 次数更少。

【总】核心结论

索引就像书的目录，先查目录再翻到那一页，不用整本书从头读。

【分】分点展开
  1. 没索引要全表扫描
  2. 有索引按 B+ 树定位
  3. 但索引占空间、拖慢写入
【总】总结升华

所以索引是用空间换时间，要按查询场景建。

【总】核心结论

InnoDB 索引是 B+ 树，聚簇索引叶子存整行、二级索引叶子存主键，因此二级索引查询可能要回表。

【分】分点展开
  1. 树矮 → IO 少：一个 16KB 页可放上千个键，三层能撑两千万行
  2. 回表代价：二级索引找到主键后再走一遍聚簇树
  3. 覆盖索引可消除回表，Extra: Using index
【总】总结升华

建索引的核心是提升区分度 + 减少回表，用 EXPLAIN 验证。

【总】核心结论

索引优化本质是在「写放大、空间、读性能」三角里做取舍，要结合优化器的代价模型来看。

【分】分点展开
  1. 优化器按基数（index dives 采样）估行数，统计信息漂移会选错索引，可用 ANALYZE TABLE 或 force index
  2. RR 下靠 next-key lock 解决幻读，间隙锁在并发插入时容易放大锁冲突
  3. 踩坑：给低区分度列建索引 + ORDER BY 文件排序，线上大事务锁表
【总】总结升华
