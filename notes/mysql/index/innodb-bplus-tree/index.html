B+ 树把所有数据都放在叶子层、非叶子层只存键和页指针，因此同样 16KB 的页能装下更多键、树更矮， 一次主键查询只需 3 次磁盘 IO；叶子层又用双向链表串起来，范围查询只需定位一次就能顺序扫描。

红黑树是二叉树，树高 log₂N，一千万行就是 24 层，而每层节点通常独占一个磁盘页 → 最坏 24 次随机 IO。

B+ 树是高 m 叉树，m（分支数）由「页大小 ÷（键 + 指针）」决定，通常上百，树高被压到 3~4 层。

Hash 只能做等值查询，= 之外（范围、排序、最左前缀匹配）全部无能为力。

而且哈希冲突退化后是不确定的，InnoDB 只在 Memory 引擎和自适应哈希（adaptive hash index）内部使用它。

按默认 innodb_page_size = 16KB、主键为 BIGINT（8 字节）+ 页指针（6 字节）估算：

-- 每个目录项：8(主键) + 6(页指针) ≈ 14 字节，再加约 1 字节记录头开销 -- 单个 16KB 页可容纳的分支数 SELECT FLOOR(16384 / 15); -- ≈ 1092 分支 -- 叶子层按每行 1KB 估算 SELECT FLOOR(16384 / 1024); -- ≈ 16 行/页

于是两层非叶子 + 一层叶子 ≈ 1092 × 1092 × 16 ≈ 1900 万行，这正是「三层能撑两千万行」这个说法的来历。

二级索引的叶子存的是主键值而不是行地址。用 UUID 做主键时，每个二级索引的每一行都要多存 36 字节， 并且随机写入造成页分裂，实测索引体积和写入抖动都明显恶化。

【总】核心结论

索引像书的目录，B+ 树能让数据库少翻几页就找到数据。

【分】分点展开
  1. 二叉树太深，每次下探都可能是一次磁盘读
  2. B+ 树一个节点是一整页，分支多、树矮
  3. 叶子之间有链表，范围查询和排序都方便
【总】总结升华

所以 InnoDB 选 B+ 树，本质是为磁盘 IO 优化的结果。

【总】核心结论

B+ 树非叶子只存键和指针、叶子存数据并双向串联，树矮且顺序友好，因此兼顾点查与范围查。

【分】分点展开
  1. 16KB 页 ÷ 15 字节目录项 ≈ 1092 分支，三层可放约两千万行
  2. 聚簇索引叶子存整行，二级索引叶子存主键，所以二级索引要回表
  3. 覆盖索引让 Extra 出现 Using index，把回表省掉
【总】总结升华

建索引的原则是提高区分度、减少回表，并用 EXPLAIN 验证。

【总】核心结论

这是「写放大、空间、读性能」三者的权衡，还要放在优化器代价模型和 buffer pool 命中率下看。

【分】分点展开
  1. 树矮的收益只在冷数据落盘时体现；热页全在 buffer pool 时，B+ 树高度差异被内存访问摊平
  2. 主键必须单调递增，否则页分裂造成碎片，实测写入吞吐下降明显，这是 UUID 主键的真实代价
  3. 统计信息靠 index dives 采样，数据倾斜时优化器会选错索引，必要时 ANALYZE TABLE 或 force index
  4. RR 隔离级别下用 next-key lock 抑制幻读，间隙锁在高并发插入场景会放大锁冲突
【总】总结升华

我的习惯是先定读写比，再从慢日志反推索引设计，最后用压测确认收益。

自增 BIGINT 主键保证 B+ 树尾部追加，避免页分裂；分库分表后再用雪花算法补全局唯一。

把 GROUP BY 维度列和聚合列一起放进联合索引，扫描走索引不回表，报表耗时降一半。

status 只有 3 个取值，建索引后优化器仍走全表扫描，白付写入代价，最后删掉。

LIMIT 500000,20 要丢弃前 50 万条，改成 WHERE id > 上次最大 id 游标翻页。

存索引列 + 主键值，不存整行。所以通过二级索引定位后，还要拿主键再走一遍聚簇树，这就是回表。

为了 BETWEEN、ORDER BY、> 这类顺序访问：定位到起点后顺着链表扫，不必回到根再下降。

插入的键落在一个已满的页中间时会分裂成两页并各占一半，产生碎片、放大写入。 单调递增主键让插入总是落在最后一页，从而规避。
